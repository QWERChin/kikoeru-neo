# 扫描与元数据

扫描把媒体库里的目录变成库里的作品和轨道。它分阶段记录状态，每个同步范围在完整列出后才提交。中断的扫描需要重新启动，已提交数据保留，目录摘要和元数据补抓规则减少重复工作，不保证自动断点续跑。

添加媒体库、目录命名、扫描操作与自动扫描设置见[媒体库与扫描](https://github.com/QWERChin/kikoeru-neo/blob/main/docs/zh-CN/libraries.md)。手动、定时和目录监听触发的扫描共用调度入口，自动化字段的合同见[接口合同](contract.md)的“自动扫描和目录监听”。

## 并发和提交边界

- 同一个媒体库同时只跑一个扫描。重复启动返回正在运行的那个任务。
- 不同媒体库的扫描排成一队，一次只跑一个，免得两个媒体库抢磁盘或 OpenList 的限流额度。排队的扫描默认按提交的先后开始，管理员可以把一个移到最前。
- 每个“同步范围”在完整列出之后才提交到数据库。作品级别的同步范围是整个媒体库的作品目录列表，轨道级别的同步范围是一部作品的完整文件树。范围内任何一次 `list` 失败，这个范围就不提交，已有的数据保持不变。
- 提交用短事务，每批最多 200 部作品。

## 阶段

1. **发现作品**：遍历媒体库，目录名里能匹配到 `RJ`、`BJ`、`VJ` 加 6 到 8 位数字的就当作一部作品，不再往里找。作品目录可以嵌在多层子目录里，最多 16 层。匹配不到编号的目录继续往下找，符号链接跳过并记进扫描日志。OpenList 的列表可能把同一个目录列两次，同一路径的目录只保留第一个，重复的记进扫描日志，否则同一个位置会插入两次，违反唯一约束，整次扫描失败。编号按数值规范化：大于等于 1000000 的补到 8 位，否则 6 位，所以 `RJ0123456` 和 `rj123456` 都是 `RJ123456`，和导入时由旧 ID 生成的编号一致。编号前面紧挨着字母时（比如 `CRJ123456`）不算。新建作品时，同一个事务里把 `legacy_user_state` 里这个编号的旧用户数据挂上去（见[迁移](migration.md)的“合并到已有的库”）。
2. **同步轨道**：列出作品目录下的完整文件树，按原始路径和库里的轨道对比。OpenList 和 WebDAV 上的作品先比较目录摘要，没有变化就跳过这一步，见[存储后端](storage.md)的“列目录优化”。新增的插入，`size` 或 `mtime` 变了的清空探测结果，不再出现的设置 `missing_at`。重新出现的轨道清掉 `missing_at`，ID 不变。最多 `list_concurrency` 部作品（本地媒体库是 4）同时列目录，写库仍按发现的顺序一部一部来，所以并发多少都得到同样的作品和轨道 ID。OpenList 客户端自己的准入窗口和限速仍是唯一的节流。
3. **抓元数据**：新作品从 DLsite 抓取元数据，规则见下文。DLsite 和存储各有自己的限速，所以发现作品之后，抓元数据和第 2 步同时开始，不等整个媒体库列完。远端列目录可能受网盘限速影响，并行抓取可以利用这段等待时间，但不保证元数据先于同步轨道完成。同时进行时进度条和 `message` 跟着同步轨道走，第 2 步结束后，没来得及抓的作品再接着抓，同一次扫描里每部作品只问 DLsite 一次。
4. **读取封面**：元数据抓完之后，这个媒体库里还没有封面的作品，从自己的文件夹里挑一张图片当封面，规则见下文的“封面”。放在元数据后面，是为了只给来源没给出封面的作品读文件，OpenList 上不多取直链。
5. **探测时长**：本地的音频和视频轨道排进轻任务队列跑 ffprobe，在后台进行，不阻塞扫描结束。OpenList 上的轨道不在扫描时探测，因为每次探测都要取一次直链，会触发网盘限流。它们在第一次播放时由 `prepare` 探测，导入的旧时长先顶上。

扫描任务运行时，`message` 写当前阶段，比如“发现作品”“同步轨道 25/100”“抓取元数据 12/40”“读取封面 3/12”，和进度一样最多每秒写一次，前端在任务列表和 SSE 里都能看到。扫描被取消时，已经提交的作品和失去位置的作品照样整理一次重复副本，但不做补匹配。

`POST /api/admin/scan` 为每个媒体库提交一个 `scan` 任务，`dedupe_key` 是 `scan:{媒体库 ID}`，在调度器的扫描通道里一次只跑一个，没有超时，排队的顺序见[媒体处理与播放](media.md)的“子进程”。扫描摘要的各项计数和扫描日志存进任务表的 `result` 列，供排查用。[接口合同](contract.md)只给转码任务返回 `result`，所以任务接口和设置页现在都看不到它们，部分作品没能列出时，设置页照样显示扫描完成，见[路线图](roadmap.md)。服务重启时，排队中的扫描任务按 `payload` 里的媒体库重新排队。媒体库连不上时任务失败，`message` 写出原因。本地媒体库新增或变化的音频、视频轨道，每部作品提交后马上各排一个 `probe` 任务（轻任务通道，`dedupe_key` 是 `probe:{轨道 ID}:{来源版本}:{大小}:{修改时间}`，文件变了就是一个新任务，不会并进还在跑的旧任务里，旧任务的结果会因为来源版本、大小或时间对不上被丢弃），不等整次扫描结束。提交在扫描任务里和扫描并行进行，所以服务关闭时调度器会等它们都写进任务表。转码的排队上限只数排队中的转码任务，大批后台探测不会让播放的转码请求得到 `queue_full`。还没探测完的轨道第一次播放时由 `prepare` 同步探测。这些步骤由 `neo-scanner` crate 的 `scan_root` 完成，它在调度器的扫描任务里运行。需要探测的本地音频、视频轨道 ID 在每部作品提交后马上交给调用方（`Observer::probe`），由调用方排进探测队列，所以取消扫描不会丢掉已经发现的探测。扫描完这个媒体库的所有作品目录之后，再对涉及的作品统一处理重复文件和导入进度的补匹配，这样同一个媒体库里有两个位置的作品，会同时看到两个位置的文件。

通过接口更换本地媒体库的位置后，即使文件路径、大小和修改时间都没变，下一次扫描也会为探测结果已失效的音频、视频轨道重新排队。更换位置时会清空作品目录摘要，扫描只在摘要尚未重建时补排没有探测结果的轨道。后台探测使用新来源版本，恢复轨道时长和作品总时长，不需要先播放轨道。ffprobe 读不出的文件仍然没有探测结果，但后续扫描不会仅因探测结果为空而重新排队。

前四个阶段完成就算这次扫描完成。任务列表会分开显示“扫描”和“后台探测”两部分，不会用一个“完成”掩盖还在跑的探测。

## 缺失和冲突

- 只有在作品级同步范围完整列出、并且确实不包含某个位置时，才给这个位置设置 `missing_at`，这个位置下的轨道也一起设置，因为它们已经没法播放。一部作品的所有位置（包括其他媒体库里的）都缺失时，作品才设置 `missing_at`。位置重新出现时，轨道由同步轨道这一步按原始路径恢复，ID 不变。
- 一部作品的文件树没能完整列出时，这部作品的轨道保持不变，记进扫描日志，其他作品照常同步。缺失的作品默认不出现在列表里，但收藏、进度和轨道都保留。
- 管理员在设置页里可以看到缺失的作品和位置（`GET /api/admin/missing`），选择“清理”后才物理删除（`POST /api/admin/missing/cleanup`）。清理只删除那时仍然缺失的行。删除作品会连同它的收藏、播放进度和导入辅助记录一起删掉，封面和缩略图文件也删掉。删除位置时，指向它的轨道的播放进度保留，只是不再指向轨道。
- 同一个编号出现在第二个位置时，加一行 `work_locations`，这个位置的文件合并到同一部作品下，规则见[数据模型](data-model.md)的“多个位置怎么合并”。扫描日志里记下这次合并，管理员可以在作品详情页看到每部作品有哪些位置。

## 抓不到元数据的作品

旧 kikoeru 在元数据抓取失败时不会把作品入库。新实现改成先入库，`metadata_src = 'none'`，标题用目录名，封面先从作品文件夹里的图片里挑，挑不出来就显示占位图。作品照样能播放。之后可以在详情页手动填写，或者等网络恢复后点“重新抓取”，只重试元数据这一步。

## 元数据来源

| 来源 | 用途 | 默认行为 |
|---|---|---|
| DLsite 作品数据接口（`product.json`） | 标题、社团、声优、标签、发售日、价格、封面 | 启用 |
| DLsite 作品信息接口（`product/info/ajax`） | 平均分、评价数、下载数、排名、价格 | 启用 |
| asmr.one 的作品信息接口 | DLsite 上已经下架的作品的标题、社团、声优、标签、发售日、封面，见下文“备用来源” | 默认关闭（`metadata.fallback`） |
| hvdb 的作品页 | DLsite 和 asmr.one 都没给出声优的 RJ 作品的声优，见下文“声优补充” | 默认关闭（`metadata.hvdb`） |

上面的标签只是原始名，入库前要按下文的“标签合并”归到规范标签上。

每个来源实现同一个 `MetadataProvider` trait，返回统一的 `WorkMetadata`。请求之间间隔至少 1 秒，失败最多重试 3 次，每次间隔翻倍。

所有来源的请求，包括下载封面，都按同一个代理设置走。管理员在设置页填了代理时只用它，没填时按 `HTTPS_PROXY`、`HTTP_PROXY`、`ALL_PROXY` 和 `NO_PROXY` 这几个环境变量，都没有就直连，规则见[接口合同](contract.md)的“服务器设置”。保存之后每个来源换一个新的 HTTP 客户端，下一个请求就用新的代理，已经发出的请求按原来的方式完成，所以正在运行的扫描不用重新开始。请求间隔照常计算，不因为换了客户端而重新开始。asmr.one 已经选好的镜像作废，下一个请求重新探测。启动时读数据库里保存的代理，读出的值不合规则时（只有手工改过数据库才会这样）记一条 WARN 并改用环境变量，服务照常启动。

DLsite 用旧服务也在用的两个 JSON 接口，不解析 HTML 作品页：它们按请求的语言（`zh_CN`，和旧服务的 `tagLanguage` 一致）直接给出名字，页面改版也不受影响。具体规则：

- 作品按编号前缀去对应的分区：RJ 在 `maniax`，BJ 在 `books`，VJ 在 `pro`。`product.json` 返回空列表或 404 算“DLsite 上没有这部作品”，连不上、超时、5xx 和读不懂的回答算“暂时无法访问”。信息接口失败不影响作品数据，只是少了评分这些数字。
- 社团 ID 按旧库的方式把 `RG`、`BG`、`VG` 编进数字（类型 × 10^9 + 编号），声优 ID 先按名字找已有的声优，没有就用旧服务的 UUID v5（同一个命名空间），所以导入的社团和声优能对上。标签先按名字找别名，再按 DLsite 标签 ID，都没有才新建，见下文“标签合并”。
- 封面只从 `img.dlsite.jp` 下载，重定向也只能留在允许的主机上，防止回答里的地址把服务器引向内网，指向别处的封面当作没有封面。封面下载遇到“暂时无法访问”时，这部作品整个留到下次再抓，元数据也先不写。封面写不进 `cache/tmp` 或 `covers/` 时也一样：只写元数据会让这部作品离开扫描要抓的那一批，之后再也没有机会补上封面，所以元数据也先不写，这一轮抓取停下，因为别的作品也会碰到同一个数据目录。下载放在写事务之外，先写进 `cache/tmp`，在事务里确认可以替换后再 rename 到 `covers/{作品 ID}.jpg`，`cover_version` 加一。旧封面先挪进 `covers/.swap`，提交成功才删掉。提交之前写库失败时，把旧封面放回原处。如果 `commit()` 返回错误，不能据此断定数据库没有提交，新旧封面和交换记录都保留，调用方仍收到原来的数据库错误。挪动之前在 `covers/.swap` 写一份记录，进程中途退出时，下次启动按数据库里的 `cover_version` 决定保留新封面还是放回旧封面，保证封面文件和 `cover_version` 一致。这个目录在 `covers/` 里面，所以备份时一起带走，从备份恢复后第一次启动同样会处理。恢复失败时服务不启动，记录和旧封面都留在原处等下次重试。替换封面期间，封面请求会等替换提交或回滚之后再读 `cover_version` 和文件，避免把新图按旧版本号缓存成缩略图。提交结果不明，或者回滚时连旧封面也放不回去时，这部作品在重启之前只显示占位图，也不再替换封面，重启时按记录恢复。待恢复期间，即使本次抓取没有封面（例如图片返回 404），也不提交这部作品的元数据，保留重启后的自动补抓资格。文件夹封面使用同一套交换和恢复规则，不依赖元数据来源是否启用。
- `metadata_src = 'manual'` 的作品，普通抓取不改元数据。`cover_src` 是 `imported` 或 `manual` 的作品，普通抓取不换封面。`POST /api/works/{id}/refresh?force=true` 两样都覆盖。
- 扫描的第三阶段只抓这个媒体库里 `metadata_src = 'none'` 的作品，每部作品一个请求间隔。第一次遇到“暂时无法访问”就停下来，剩下的作品留到下次扫描再试，所以断网时扫描不会为每部作品各等一轮重试。抓不到的作品照样能播放。
- `POST /api/works/{id}/refresh` 提交一个 `metadata` 任务（轻任务通道，`dedupe_key` 是 `metadata:{作品 ID}`，5 分钟超时），服务重启后排队中的会重新排队。

### 备用来源

DLsite 抓不到的作品（已经下架，或者 DLsite 暂时连不上）只能停在 `metadata_src = 'none'`。打开 `metadata.fallback = "asmr_one"` 之后，这种作品改从 asmr.one 的公开接口取元数据，行为和旧 kikoeru 0.6.17 的 `src/scraper/asmrOne.ts` 一致。该来源默认关闭，测试只用假服务器。

- 来源按顺序组成一条链，DLsite 永远在第一位。DLsite 抓取失败时（回答没有这部作品，或者暂时无法访问）问 asmr.one，和旧版一样。代价是 DLsite 暂时连不上时抓到的作品会记成 `asmr_one`，之后的普通重新抓取会先问 DLsite 并换回 DLsite 的数据。两个来源都暂时无法访问时，作品留在 `none`，扫描的第三阶段停下来，留到下次再抓。两个来源都没有这部作品时同样留在 `none`，作品照样入库、能播放，这一点和旧版不同（旧版不让它入库）。
- **镜像。** asmr.one 有几个地址，默认按顺序是 `https://api.asmr.one/`、`https://api.asmr-200.com/`、`https://api.asmr-100.com/`、`https://api.asmr-300.com/`（`metadata.asmr_one_urls`）。第一次需要时按顺序探测 `GET api/workInfo/1`，每个地址等 5 秒，得到任何 HTTP 回答（包括 404）就选它，连不上、超时和 5xx 就试下一个。选中的地址缓存 20 分钟，之后重新探测。全都不可用时这一次算暂时无法访问。探测路径可能返回 404，因此这里检查服务是否响应，不要求探测作品存在。
- 每个请求都带 `Cookie: locale=zh-cn`，和旧版一样，标签名因此是中文。
- **作品信息。** 只用于 RJ 编号的作品：asmr.one 只按数字归档，BJ123456 会拿到 RJ123456 的记录。`GET {镜像}api/workInfo/{编号的数字部分，去掉前导零}`，例如合成编号 RJ01234567 对应 `api/workInfo/1234567`。回答里的 `source_id` 不是同一个 RJ 编号时当作没有这部作品。解析器读取的字段包括：`title`、`circle`（`name` 和形如 `RG01234567` 的 `source_id`，解析不出社团编号时回退到顶层的 `circle_id`）、`release`（`YYYY-MM-DD`）、`nsfw`、`dl_count`、`price`、`rate_average_2dp`（没有评分时是整数 0）、`rate_count`、`rate_count_detail`、`rank`（可能是 `null`）、`vas`（只读 `name`）、`tags`（`name` 和 `i18n.zh-cn.name`）、`mainCoverUrl`。`circle.id` 和 `vas[].id` 不使用。404 算“没有这部作品”，连不上、超时、5xx、429 和读不懂的回答算“暂时无法访问”。
- 社团 ID 从 `circle.source_id` 按和 DLsite 一样的规则编进数字，所以同一个社团不会因为来源不同而分成两个。没有 `source_id` 时用 `circle_id` 当作 RG 编号。声优按名字找已有的，没有就按 DLsite 的规则生成 UUID v5，不用接口给的 `id`。标签用 `i18n.zh-cn.name`，没有时用 `name`，只按名字找别名，不使用 asmr.one 的标签 ID，因为它和 DLsite 的不是同一套编号。
- **封面。** 用作品信息里的 `mainCoverUrl`。它的协议、主机和端口必须和选中的镜像一致，下载时的重定向只能转到配置里的镜像来源（不限于选中的那个），否则当作没有封面，免得回答里的地址把服务器引向内网。其余规则和 DLsite 的封面一样，`imported` 和 `manual` 的封面照旧受保护。
- **封面备用。** 打开备用来源之后，DLsite 的封面下载失败时（下载地址回答 404，或者暂时无法访问），改从 asmr.one 的 `mainCoverUrl` 下载这部作品的封面，和旧版 `getCoverImageCore` 一样。asmr.one 也拿不到时，按 DLsite 原来的规则处理：暂时无法访问就整部作品留到下次再抓。
- 请求之间至少间隔 2 秒，比 DLsite 更慢，因为 asmr.one 是个人运营的站点。失败最多重试 3 次，每次间隔翻倍。429 和 503 按 `Retry-After` 等待，单次调用最多等 120 秒，超过就算暂时无法访问。镜像探测不重试。
- 从备用来源抓到的作品 `metadata_src = 'asmr_one'`。之后的普通重新抓取仍然先问 DLsite：DLsite 能抓到就换成 DLsite 的数据，`metadata_src` 变回 `dlsite`。抓不到就用备用来源覆盖。`manual` 的保护规则对两个来源一样。
- 扫描的第三阶段照旧只抓 `metadata_src = 'none'` 的作品，所以打开备用来源之后，以前停在 `none` 的作品会在下一次扫描时从备用来源补上。

### 声优补充

DLsite 的作品数据里有些作品没有声优，多半是社团没有填。旧 kikoeru 0.6.17 在这种时候去 hvdb（`https://hvdb.me/`，社区维护的同人音声数据库）的作品页找声优名字，见旧版的 `src/scraper/hvdb.ts`。打开 `metadata.hvdb = true` 之后行为相同。默认关闭，测试只用假服务器。

- **各字段从哪里来。** 先按上文的来源链得到一份元数据：DLsite 抓到就用 DLsite 的，DLsite 失败时用 asmr.one 的。这份元数据的所有字段都来自同一个来源，`metadata_src` 也记成这个来源。hvdb 只补一个字段：这份元数据的声优列表是空的，作品又是 RJ 编号时，才去问 hvdb，把找到的名字当作声优。hvdb 不改标题、社团、标签、发售日、评分和封面，它的标签是社区用英文起的名字，和 DLsite 的标签不是一套，标题只有日文。`metadata_src` 没有 `hvdb` 这个值。
- **请求。** `GET {metadata.hvdb_url}Dashboard/Details/{编号的数字部分，去掉前导零}`，比如 RJ01234567 是 `Dashboard/Details/1234567`，回答是 HTML 页面。客户端直接请求这个路径，每次查询只发一个请求，间隔规则不会被重定向绕过。不跟随重定向，遇到重定向当作没有找到。不认识的编号回答 500，没有 404。
- **读页面。** 页面的 `<title>` 是 `HVDB - {编号}`，其中编号的数字部分和请求的不一致时当作没有找到。声优是指向 `/Dashboard/CVWorks/{数字}` 的链接，取链接文字。同一个人通常有罗马字和日文两个写法，所以和旧版一样丢掉含拉丁字母的名字，剩下的去重并保持页面上的顺序。声优 ID 按名字找已有的，没有就按 DLsite 的规则生成 UUID v5，和其他来源一致，不用 hvdb 的数字。
- **失败。** hvdb 只是补充，所以它的任何失败（连不上、超时、500、页面读不懂、没有声优）都只是让这部作品没有声优，其余元数据照常写入，扫描也不因此停下。日志里记一行。之后的普通重新抓取会再问一次。旧版这时会写一个占位声优，这里不写，列表里就是没有声优。
- 请求之间至少间隔 2 秒，单次请求 10 秒超时（旧版的 `hvdbTimeout`）。连不上、超时、429、502、503 和 504 最多重试 3 次，每次间隔翻倍，429 和 503 按 `Retry-After` 等待，单次调用最多等 120 秒。500 不重试，因为它就是 hvdb 对不认识的编号的回答。
- `metadata.source = "none"` 时不起作用。BJ 和 VJ 编号不问 hvdb，旧版也只问 RJ。

## 标签合并

DLsite 同一个标签在不同语言的页面上名字不同，改过名的标签也有新旧两种写法。抓取、导入和手动编辑都把它们归到同一个规范标签上：

- 抓到元数据时，原始标签名先查 `tag_aliases`，查到就挂到对应的规范标签上。查不到时，带 DLsite 标签 ID 的名字归到这个 ID 的标签，标签还不存在就用这个名字新建，原始名同时记成它的别名。DLsite 按 `zh_CN` 抓取，每个标签都带 ID，所以同一个 DLsite 标签换了写法也落在同一个标签上，规范名是第一次见到它时的写法。
- 旧库导入的标签沿用旧服务记下的 ID，从 DLsite 抓来的就是 DLsite 的标签 ID，之后抓到的同一个标签和它对得上。
- 手动编辑时新写的标签名、以及抓取时没有 DLsite 标签 ID 的名字（asmr.one 只给名字），查不到别名时新建的规范标签从 1000000 开始编号，不会和 DLsite 的标签 ID 冲突。这类名字和 DLsite 抓过的写法不同时会多出一个标签，由管理员合并。
- 管理员可以用 `POST /api/admin/tags/merge` 把两个标签合并：作品关联和别名都转到目标标签，被合并的标签名也记成目标标签的别名。被合并掉的标签记在 `tag_merges` 表里，之后按它的 DLsite 标签 ID 抓到的名字落到合并后的标签上。
服务没有内置标签词典，也不在启动时同步或导出词典。已有的标签与别名保留，由抓取、导入和管理员合并继续维护。

## 封面

- 抓元数据时下载 DLsite 的主图，存成 `covers/{作品 ID}.jpg`，`cover_src = 'dlsite'`。
- 来源没给出封面的作品（DLsite 连不上、作品已经下架、DLsite 没有主图，或者 `metadata.source = "none"`），扫描的第 4 步从作品自己的文件夹里挑一张图片，转成宽度不超过 1200 像素的 JPEG 存起来，`cover_src = 'folder'`。DLsite 的封面是官方主图，每部作品都是同一种图，文件夹里的图片命名不统一，还常有特典插画、壁纸、角色介绍和音轨列表，所以文件夹只做后备：之后抓到 DLsite 的封面时，普通的抓取照常替换它。
- 挑图只看路径，不读文件。候选是这个媒体库里没有缺失的 jpg、jpeg、png 和 webp，大小不超过 32 MiB。另一个媒体库里有同一个文件时，这里的副本照样算候选，因为那个媒体库可能正好读不了。解码时长宽都不能超过 16384 像素，压缩得很小的超大图片在分配内存之前就被拒绝。文件名里有别的作品编号的图片不用，作品文件夹里有时放着别的作品的封面当广告。编号按第 1 步的规则规范化之后再比较，所以 `RJ0123456_img_main.jpg` 算作 `RJ123456` 自己的图片。排序从好到差：文件名同时有本作品编号和封面类的词（`img_main`、封面、表紙、ジャケット、cover、アートワーク、主視覺 这类，或者单独的 `main`），只有封面类的词，只有本作品编号，所在目录名有封面类的词，文件名有插图类的词（插图、イラスト、缩略图、thumbnail 这类），所在目录名有插图类的词。哪一条都不满足的图片不用，这部作品继续显示占位图。同一档里，名字有差分、草稿、线稿、壁纸、立绘、角色介绍、音轨列表这类词的排在后面，然后不小于 32 KiB 的按大小从小到大，大小未知的其次，更小的最后，因为封面最多显示几百像素宽，而 OpenList 上的每个字节都要经过网盘。规则写在 `neo-scanner` 的 `metadata/folder.rs`。
- 每次扫描每部作品最多读一张图。文件不存在、太大或者不是能解码的图片时，记下这个文件（轨道 ID 和大小），服务这次运行期间不再读它，下次扫描换下一张候选。存储连不上、取得文件来源或打开远端流时存储后端返回上游错误（包括 OpenList 刷新直链后仍返回 401 或 403）、网盘回答 429 或 5xx、本地文件打开之后读不出来，或者封面目录写不进去时，这一步停下，剩下的作品留给下次扫描，和抓元数据一样，这些情况都不记失败。访问恢复后，即使轨道 ID 和大小没有变化，下次扫描也会重新读取。
- 缩略图按需生成：宽 480 像素，保持原比例，存在 `cache/thumbs/{作品 ID}-{cover_version}.jpg`。同时只生成 2 张，先写临时文件再 rename。
- 封面替换后 `cover_version` 加一，缩略图的文件名、URL 和 `ETag` 都随之变化，所以浏览器确认缓存时，封面没换就只收到 304。
- 作品没有封面时，接口返回一张占位图。

## 中文和日文文件名

部分旧作品的文件名是 GBK 或 Shift_JIS 编码。数据库里按原始字节保存路径，读文件时直接用原始字节。如果原始字节不是合法的 UTF-8，用 `chardetng` 猜编码生成 `display_path`，只用于显示和搜索。猜编码按路径的每一段分别做，UTF-8 目录里的一个 GBK 文件名不会把目录名也一起解成乱码。猜错了只会影响显示，不会打不开文件。NFC 规范化也只用在显示和搜索上，不用来合并两个不同的文件。

旧 kikoeru 的“修复乱码”功能会直接重命名磁盘上的文件，新实现不做这个写操作。
