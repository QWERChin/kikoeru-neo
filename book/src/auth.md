# 认证与用户

kikoeru-neo 主要是单用户使用，但保留多用户的能力：一个或多个管理员，加若干普通用户。普通用户能浏览、播放、收藏，管理员额外能管理媒体库、扫描、改元数据和查看全部任务。创建、删除用户和创建管理员通过服务器上的本地命令完成，网页没有用户列表管理。所有访问都需要登录，不提供匿名模式。

账号初始化、密码重设和删除步骤见[账号指南](https://github.com/QWERChin/kikoeru-neo/blob/main/docs/zh-CN/accounts.md)，代理与凭据的部署边界见[安全与网络](https://github.com/QWERChin/kikoeru-neo/blob/main/docs/zh-CN/security.md)。

## 密码

密码只用 argon2id 存储，不实现旧 kikoeru 的密码校验。导入账号的 `password_hash` 留空，必须设置新密码后才能登录，避免把旧密钥和校验机制带进新系统。

创建用户和管理员初始化由本地命令负责，网页没有用户列表管理接口。网页允许用户修改自己的密码和退出所有设备。新库没有管理员时服务仍可就绪，登录返回 `setup_required`，不能把就绪检查当作初始化完成证明。

## Token

登录返回一个 JWT。签名算法固定为 HS256，验证时不接受 token 头里声明的其他算法。payload 包含这些字段：

| 字段 | 含义 |
|---|---|
| `sub` | 用户 ID |
| `ver` | 签发时用户的 `token_version` |
| `aud` | 用途：`api` 或 `media` |
| `iat`、`exp` | 签发和到期时间，按 JWT 标准用秒，不是业务 API 用的毫秒 |

`sub` 按 JWT 标准写成字符串形式的用户 ID。用户 ID 不复用（见[数据模型](data-model.md)），新建用户的 `token_version` 也从一个随机的 32 位数开始，而不是 0。这样即使某一行以后拿回了旧的 ID（比如把备份导进一个新库），旧账号的 token 也对不上它。

API token 有效期 30 天，媒体 token 6 小时。每次验证都查一次用户表：用户还存在，`ver` 等于当前的 `token_version`，才算有效。改密码（包括服务器上的 `user set-password`）或在设置页点“退出所有设备”时递增 `token_version`，删除用户则因用户行不存在而拒绝验证。这些操作都撤销该用户已签发的 API token 和媒体 token。只退出当前设备不需要服务端参与，前端丢掉自己保存的 token 即可。管理员权限每次从用户表读取，不放进 token。

签名密钥在首次启动时随机生成，存在数据目录下权限为 `0600` 的 `secrets/jwt.key` 文件里，不写进配置文件，也不在构建时生成。旧 kikoeru 的 jwt 密钥不复用，切换之后需要重新登录一次。

## 密码错误的次数限制

登录和修改密码（`PUT /api/auth/password` 校验当前密码）共用同一套限制。每次密码校验失败都计数，用户名不存在、账号没有密码、密码错误都一样。登录时按请求里的用户名计，改密码时按当前用户计。成功不清零任何计数。`setup_required` 不算失败，因为这时没有校验密码。用户不存在或者没有密码时，服务也拿一个参数相同的假 argon2id hash 校验一次，让失败的耗时不透露账号是否存在。

| 计数对象 | 窗口 | 超过之后 |
|---|---|---|
| 客户端地址 | 当前和上一个 1 分钟窗口，合计 1 到 2 分钟 | 达到 10 次失败后，这个地址的请求一律返回 429 `too_many_attempts`，密码正确也一样 |
| 用户名 | 当前和上一个 5 分钟窗口，合计约 10 分钟 | 达到 20 次失败后，针对这个用户名的每个请求先等 1 秒再校验密码，但从不拒绝 |
| 全部请求 | 当前和上一个 1 分钟窗口 | 达到 200 次失败后，所有登录和改密码请求都先等 1 秒 |

用户名和全局计数只会减速，不会封锁。别人猜管理员的用户名，只能让主人登录慢 1 秒，不能把主人锁在外面。没有超过自己地址限制的客户端，用正确的密码总能登录。

**先计数，后校验。** 每次校验密码之前，服务在同一把锁里先判断是否超限，再把这次记成一次失败，所以并发的请求不会一起越过限制。校验中途出错、客户端断开时，这次仍然算失败。只有密码正确时才把这次退回，退回只作用在当初计数的那个窗口，那个窗口已经过期时什么也不做。

**日志。** 每次密码校验失败（登录或改密码）记一条 WARN，因限流返回 429 时也记一条 WARN，登录成功记一条 INFO，都带用户名和按下面规则取到的客户端地址，所以有人在试密码时从日志里看得出来。密码从不写进日志。用户名来自请求，日志里最多留 64 个字符，并按转义后的形式写出，换行之类的字符不能伪造出一行假日志。

**地址怎么取。** 默认取 TCP 连接的对端地址，只看地址不看端口，IPv6 按 /64 前缀计数。只有对端地址在配置的 `trusted_proxies` 里时，才改用 `X-Forwarded-For` 的最后一项，也就是这个代理自己追加的那一项。`listen` 是 `[::]` 时，IPv4 的代理连进来显示成 `::ffff:127.0.0.1` 这样的映射地址，比较时它和 `127.0.0.1` 算同一个。前面的项由客户端控制，不可信。只支持一层代理。

**计数怎么存。** 地址和用户名各用一个固定大小的 count-min sketch（4 行，每行 4096 个计数器），每个窗口一份，计数只在内存里，服务重启后清零。用户名超过 64 个字符的部分不参与计数，因为数据库里的用户名最多 64 个字符。sketch 没有按键的表，也不淘汰任何项，所以内存固定，攻击者用大量新地址或新用户名既冲不掉自己的计数，也填不满什么表。哈希种子在每次启动时随机生成，攻击者没法事先算出和别人冲突的键。

**剩下的风险。**

- 哈希冲突只会多计，不会少计。在大规模攻击下，一个无辜的地址可能因为 4 个计数器都和攻击流量撞上而被误判。按泊松分布估算，2 分钟里有 1 万个不同来源各失败一次时，一个无辜地址被误判的概率远小于百万分之一。来源数到 4 万左右时，大约一成的无辜地址会被误判。
- 同一个 NAT 或者代理后面的所有客户端共用一个地址计数，其中一个人猜密码会让其他人也收到 429。没有配置 `trusted_proxies` 却放在反向代理后面时也是这样，所有客户端共用代理的地址。
- 攻击者如果有很多地址，每个地址每 2 分钟最多试 10 次，再加上用户名的减速。这能拖慢但挡不住大规模的猜测，密码本身仍然要足够长。

## 媒体请求的认证

audio 和 video 元素不能带 `Authorization` 头，所以媒体接口另外接受 `?token=`，但只接受 `aud = media` 的媒体 token。前端用 API token 调用 `POST /api/auth/media-token` 换一个媒体 token，再拼到媒体 URL 上。

媒体 token 只能访问这些路由，并且只能用 GET 和 HEAD：

- `/api/tracks/{id}/stream`
- `/api/tracks/{id}/playable`
- `/api/tracks/{id}/download`
- `/api/tracks/{id}/subtitle`
- `/api/tracks/{id}/hls/index.m3u8` 和 `/api/tracks/{id}/hls/{set}/{segment}`
- `/api/works/{id}/cover`
- `/api/works/{id}/download`

它不能访问其他任何接口，也不能用来换新的 API token。

封面另外从 cookie 里读媒体 token，其他接口不读这些 cookie。`<img>` 的地址里带着 token 时，token 每 6 小时一换，所有封面的地址跟着变，浏览器缓存的封面就全部作废，要重新下载。前端拿到媒体 token 时同时写这个 cookie（`Path=/api/works`、`SameSite=Strict`），退出时删掉，封面地址不再带 token。HTTPS 下的 cookie 叫 `__Secure-kikoeru-media` 并带 `Secure`，纯 HTTP 下叫 `kikoeru-media`。HTTPS 写下的 `Secure` cookie 不能被同一主机的 HTTP 页面覆盖，共用一个名字时，先用 HTTPS 登录过的浏览器在 HTTP 下就写不进自己的 token。浏览器禁用 cookie 时，以及加载失败、换过 token 后的那一次重试，封面地址仍然带 token，所以 cookie 出了任何问题，封面也只是多请求一次，不会加载不出来。封面地址不带 token，谁都猜得到，所以封面不让浏览器不经确认就从缓存里拿：回答是 `private, no-cache` 加 `ETag`，每次显示都带着 cookie 确认，没变时只回 304。退出登录后 cookie 被删掉，同一个浏览器里的人再打开缓存过的封面地址只会得到 401。HTTPS 下退出时两个 cookie 都删，因为 HTTP 的那个也会随 HTTPS 请求发出。HTTP 下退出删不到 `Secure` 的那个，它留到过期（最多 6 小时），但只会随 HTTPS 请求发出，所以只有同一台主机 HTTP 和 HTTPS 混着用的浏览器会碰到。两个 cookie 都在时，每个先查用户表确认没有被吊销，再试下一个，所以一个被吊销的旧 token 不会挡住另一个有效的。cookie 里就是同一个媒体 token，过期、退出所有设备和改密码照样让它失效。`SameSite=Strict` 让别的网站引用封面时浏览器不带这个 cookie，封面接口又只读不写，所以它不带来跨站请求的问题。它不设 `HttpOnly`，因为前端要在退出时删掉它，而同一个 token 本来就存在 `localStorage` 里。

媒体 token 过期时，播放器在下一次请求失败后先记下当前位置，换一个新的媒体 token，再从同一位置继续，最多重试 2 次。访问日志在写入前去掉 `token` 参数，反向代理的日志也要做同样的配置（见[安全与网络](https://github.com/QWERChin/kikoeru-neo/blob/main/docs/zh-CN/security.md)）。后端代理网盘时，不会把 kikoeru 的 token 转发给上游。
