# 配置与持久状态

配置层负责选定持久状态的位置、校验启动参数，并让服务器与管理命令打开同一个数据库。本章说明这些实现约束。配置参数与操作步骤见[配置指南](https://github.com/QWERChin/kikoeru-neo/blob/main/docs/zh-CN/configuration.md)，备份与恢复步骤见[备份与恢复](https://github.com/QWERChin/kikoeru-neo/blob/main/docs/zh-CN/backup-restore.md)。

## 四类文件

| 类别 | 例子 | 谁写 | 是否备份 |
|---|---|---|---|
| 只读配置 | `config.toml` | 用户或 Nix 模块 | 由部署配置管理 |
| 外部密钥 | OpenList 和 WebDAV 密码文件 | 用户或密钥管理工具 | 由密钥管理工具负责 |
| 服务状态 | 数据库、生成的签名密钥、封面、用户字幕、导入辅助数据 | kikoeru-neo | 必须备份 |
| 可重建缓存 | 转码结果、缩略图 | kikoeru-neo | 不需要 |

服务从不修改配置文件，所以配置文件可以放在只读的 Nix store 或 `/etc` 下。服务自己生成的东西（比如 JWT 签名密钥）只写进数据目录。在界面里添加的媒体库也一样，存在数据库里，OpenList 和 WebDAV 密码存在 `secrets/roots/` 下，都随备份一起导出，见[接口合同](contract.md)的“媒体库管理接口”。设置页里的元数据代理同样存在数据库里，不属于文件配置，见接口合同的“服务器设置”。

## 配置解析与启动边界

配置解析集中在 `neo-server::config`，命令行由 `main::library` 统一选择数据目录、配置文件和数据库。显式数据目录优先于环境变量，不默认使用当前目录，避免误建新库。`serve` 的显式配置路径优先于环境变量，之后才使用数据目录中的默认文件。只有默认文件缺失时允许采用默认配置，显式文件缺失必须报错。

文件解析拒绝未知字段。先验证文件内容，再应用数据库和监听环境覆盖，不能靠环境变量掩盖非法文件配置。`serve` 之外的管理命令复用数据库选择逻辑，旧库导入的 `--config` 则属于源格式，不能被误用作新服务配置。

NixOS 模块的命令包装器默认设置配置路径和数据目录，确保账号、备份和服务使用同一数据库。这个默认不能因传入另一个数据目录而隐式消失，否则管理命令可能悄悄从 PostgreSQL 切到一个空 SQLite 文件。副本操作需要显式选择独立配置，具体步骤留在使用指南。

服务只在启动时读取文件配置，不回写文件。界面媒体库和元数据代理是数据库中的可变状态，修改通过对应接口生效。`public_url` 当前没有功能消费者，媒体和 HLS 链接是相对地址，不能把该字段当成网络入口配置。

## 数据库选择

未配置数据库地址时，状态使用数据目录中的 SQLite。服务器支持 PostgreSQL URL，配置层只接受 `postgres://` 和 `postgresql://`。数据库连接的错误输出必须隐藏密码。桌面嵌入入口忽略 PostgreSQL 设置，始终使用本机 SQLite，见[桌面版](desktop.md)。

全量旧库导入和引导式迁移生成 SQLite，合并模式可以写入已有 PostgreSQL。跨后端复制只移动数据库，签名密钥、凭据、封面和字幕仍属于数据目录。这两个持久状态部分不能在部署时拆散。

## 数据目录结构

```text
$KIKOERU_DATA_DIR/
  neo.sqlite3          数据库（WAL 模式下还有 -wal 和 -shm 文件）
  secrets/jwt.key      签名密钥，权限 0600
  secrets/roots/       界面里添加的 OpenList 和 WebDAV 媒体库的密码，数据库引用的版本化文件，权限 0600
  import-report.json   导入报告，只有 import-legacy 生成的数据目录才有
  serve.lock           运行中的服务持有它的锁，同一个数据目录上的第二个服务在动任何东西之前就退出
  covers/              封面原图，按作品 ID 命名
  lyrics/              用户保存的字幕
  cache/
    transcode/         转码后的音频（.m4a）和视频的 HLS 目录（.hls/）
    thumbs/            封面缩略图
    tmp/               生成中的临时文件，启动时清空
```

服务新建的目录权限是 `0700`，数据库文件是 `0600`，SQLite 的 `-wal` 和 `-shm` 文件沿用数据库的权限。签名密钥由 `serve` 首次启动时生成：先用 `O_EXCL` 和 `0600` 新建一个这次调用独有的临时文件写入，再用硬链接发布成 `jwt.key`。硬链接在 `jwt.key` 已经存在时会失败，不会覆盖，所以两个进程同时首次启动时，后到的那个会放弃自己的密钥，改读先发布的那个，两边签名用的始终是磁盘上那一份。密钥也从来不会对其他用户可读。启动时检查这些权限，下面任何一种情况都让服务拒绝启动，错误信息里写出路径和实际权限：

- 数据目录或数据库文件对同组或其他用户可写。数据目录是 `0755` 这样只读的没有问题，systemd 的 `StateDirectory` 默认就是这样。数据目录可以是符号链接，此时检查实际目标目录的权限。
- `secrets/` 目录或 `jwt.key` 对同组或其他用户有任何权限。
- `jwt.key` 不是普通文件，比如是一个符号链接，不管它指向哪里。

签名密钥是持久身份的一部分。替换密钥会使此前签发的 token 失效，因此备份必须同时保留数据库和密钥。

### 媒体库密码的发布与回收

界面管理的远端媒体库把密码版本号与地址一起保存在 `root_settings.settings` 中，文件名为 `secrets/roots/<id>.<version>.password`。版本号是随机生成的 128 位十六进制串，不是密码摘要。每次新密码先以 `0600` 和独占创建写入新文件，同步文件内容，在 Unix 上还同步目录项，然后提交包含地址和版本号的数据库事务。文件一经发布就不再覆盖，所以事务提交前读到旧地址和旧密码，提交后读到新地址和新密码。已建立的存储客户端继续持有原来那一对凭据。

旧数据目录仍可读取：设置没有 `password_version` 时，读取原来的 `<id>.password`。省略密码的同服务器修改保留当前引用，明确提交新密码才切换到版本化文件。请求和响应字段不变，版本号不出现在 API 响应中。沿用密码时以数据库中同一行的地址和引用为准，不使用可能落后于提交结果的内存设置。

修改、删除和启动回收都持有 `secrets/.lock`，备份也持有同一把锁。回收先读取所有已提交行的引用，包括被配置文件遮蔽的媒体库，再删除不再被引用的密码文件。SQLite 使用 WAL 的 `NORMAL` 同步模式，因此删除前必须完成一次完整检查点，避免断电后数据库恢复旧引用而文件已经删除。检查点繁忙、读取失败或设置无法解析时保留文件并记录警告，后续修改或启动重试。数据库提交报错也不回滚密码文件，因为提交可能已经成功，只是确认丢失。崩溃留下的新文件、旧文件和未写完的文件都由同一回收流程处理，回收中途再崩溃也不会删除仍有引用的版本。

停服先关闭媒体库修改的准入，再等待已接收的修改，包括等待进程内修改锁或 `secrets/.lock` 的任务。进入持久化阶段的修改由独立任务完成，请求断开不会取消它。关闭期限耗尽时，后台清理仍持有数据库和 `serve.lock`，直到这些修改、调度任务及数据库关闭全部结束，才允许下一实例启动。期限不延长，旧实例也不能在释放实例锁后再开始写入密码。

## 日志

日志写到 stderr，由 systemd 或 Docker 收集和轮转，服务自己不写日志文件。桌面版另外写日志文件，见[桌面版](desktop.md)的“日志”。stderr 接在 journald 上时（systemd 设置的 `JOURNAL_STREAM` 和 stderr 的设备号、inode 一致），每行前面带上 syslog 级别（一条消息跨多行时，比如带原文片段的 TOML 错误，每一行都带），systemd 把它记成这一行的级别并去掉前缀，所以 `journalctl -p warning` 能只列出警告和错误。在终端、Docker 里和重定向到文件时没有这个前缀。

每个请求结束时记一行访问日志，带方法、去掉 `token` 参数的地址、状态码和耗时，处理这个请求时记下的其他行也带着方法和地址。5xx 的访问日志是 WARN，原因由出错的地方另记一行，级别按原因定：媒体库连不上是 WARN，数据库出错是 ERROR。所以合同规定的 503（比如 `storage_unavailable`）只留下两行 WARN，不会出现 ERROR。

发送文件的请求成功时只记 DEBUG，默认看不到：音频流（`/stream`）、HLS 分片、封面和前端文件。播放器按字节范围一段一段地取音频，这些行原来占了访问日志的大半，把真正的警告淹没了。状态码是 4xx 或 5xx 时照常记录。访问日志的目标是 `neo_server::http::access`，请求的 span 是 `neo_server::http`，所以只调低访问日志不会让其他行丢掉方法和地址。

登录成功、密码校验失败和因限流被拒绝各记一条日志，带用户名和客户端地址，见[认证与用户](auth.md)的“密码错误的次数限制”。

后台任务的某一步失败时，任务的 `message` 只写失败的是哪一步（比如“保存响度失败”），因为它会显示给用户。数据库或文件系统给出的原因写进日志的 WARN，带任务 ID 和轨道 ID。

每个后台任务结束时都记一行 `task ended`，带任务 ID、种类、结束状态、`payload` 和 `message`，探测是 DEBUG，其余是 INFO，理由见[媒体处理与播放](media.md)的“子进程”。设置页默认不列出的响度分析靠这一行查。

## 备份

备份布局与在线数据库后端无关。`backup` 统一导出 `neo.sqlite3`，并复制 `secrets/`、`covers/`、`lyrics/` 和存在时的 `import-report.json`。配置、外部密钥和原始媒体不属于应用状态导出，缓存可以重建。

SQLite 使用 `VACUUM INTO` 在读事务中导出包括 WAL 内容的快照，不运行迁移。PostgreSQL 使用只读 `REPEATABLE READ` 快照导出为 SQLite，源迁移版本必须与程序一致。

备份在导出数据库和复制文件期间持有封面锁与媒体库凭据锁，避免数据库版本和外部文件错位。目标必须不存在、父目录必须存在，解析符号链接后仍不能位于数据目录内，以免递归复制自己。复制不跟随符号链接，输出目录和文件限制为拥有者可访问。

## 在 SQLite 和 PostgreSQL 之间搬库

`db copy` 的源只读，目标 SQLite 文件必须不存在，目标 PostgreSQL 必须为空或仅有本程序的空表。源迁移版本必须与程序一致，不能把复制当作跨版本升级。

复制在一个事务内逐表写入并核对行数，失败回滚，失败的新 SQLite 文件删除。读取快照之后产生的写入不会进入目标，所以切换数据库必须在停服边界进行。运行过目标服务后可能已经写入业务数据，不能再假定它满足空目标约束。

操作步骤见[配置指南中的数据库切换](https://github.com/QWERChin/kikoeru-neo/blob/main/docs/zh-CN/configuration.md)。
