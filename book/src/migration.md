# 从旧 kikoeru 迁移数据

导入工具读取旧 kikoeru-express 的数据副本，不修改源库。全量导入写入新的空数据目录，已有媒体库则只合并用户状态。两种方式都保留能够映射的数据，并在报告中列出跳过或无法匹配的记录，不要求新后端兼容旧表结构。

全量导入、合并、密码设置和旧容器迁移的操作步骤见[迁移指南](https://github.com/QWERChin/kikoeru-neo/blob/main/docs/zh-CN/migration.md)。本章保留发现、快照、映射、事务和补匹配规则。

## 找旧数据

`--source` 可以指向旧安装的任何一层：数据目录本身、其中的 `sqlite/` 或 `config/`、`sqlite/db.sqlite3` 文件，或者 Docker 卷的目录（库在它下面的 `_data` 里）。导入工具按下面的顺序找数据库，找的时候只看目录项和文件开头的 16 字节（SQLite 文件头），不打开旧库，因为打开本身就可能在旧库旁边留下 `-wal` 和 `-shm` 文件。

1. 选的是文件：文件头必须是 SQLite，否则直接拒绝。
2. 选的是目录：依次看 `sqlite/db.sqlite3`、`db.sqlite3`（选的是 `sqlite/`）、上一级的 `sqlite/db.sqlite3`（选的是 `config/` 或 `covers/`）。
3. 都没有时，看下一层的子目录。只有一个子目录像旧数据目录时用它，并读取该安装的 `config.json`，按其中的设置定位数据库、封面和媒体库。即使默认位置还留着数据库文件，也以配置指定的位置为准，显式路径覆盖仍然优先。有多个时（比如每个旧版本一个文件夹）列出来，由用户选。

封面目录取数据库所在 `sqlite/` 旁边的 `covers/`。数据库不在 `sqlite/` 里时没有默认位置，所有作品都报告缺封面，可以用 `--covers` 指定。`--db` 和 `--covers` 也能单独指定数据库和封面目录，优先于自动查找。

报告开头列出数据库和封面的路径和来源：`given` 是用户指定的，`default` 是旧布局里的固定位置，`guessed` 是从旁边的目录推出来的（第 2 步的上一级和第 3 步）。推出来的路径不一定是用户想要的那份数据，所以要加 `--accept-guessed` 确认后才继续。

导入的目标不能和用户选的路径、数据库所在目录、`sqlite/` 上面的数据目录或封面目录重叠，解析符号链接后再比较。

## 读旧的 config.json

导入工具读旧的 `config.json`，但只读白名单里的字段：`version`、`sqliteType`、`dbUseDefaultPath`、`databaseFolderDir`、`coverUseDefaultPath`、`coverFolderDir`、`auth`，以及 `rootFolders` 每一项的 `name`、`type`、`path`、`url`、`basePath`、`username`。这些字段之外的键（包括 `jwtsecret`、`md5secret`、`mysqlConnection` 和 OpenList 的 `password`）不是任何结构体的字段，serde 解析时直接跳过，不保存它们的值。报告、JSON 输出、错误信息和日志里都不会出现它们，测试检查了这一点。

- **在哪里找。** 用户选的目录里的 `config/config.json` 或 `config.json`（选的是 `config/`），Docker 卷则看 `_data` 里的这两处。选的是 `sqlite/` 或其中的 db 文件时，只看旁边的 `config/config.json`。不往更上层的目录找，否则别处放着的一个 `config.json` 就能把导入引到另一个数据库。`--config` 可以直接指定。
- **数据库类型。** `sqliteType` 不是 `sqlite3` 时（MySQL 版）直接拒绝，因为没有 SQLite 文件可读。
- **旧路径怎么换到这台机器上。** 旧配置里的路径是旧机器或旧容器里的路径，比如 `/usr/src/kikoeru/VoiceWork` 或 `C:\kikoeru\VoiceWork`。按下面的顺序换：
  1. `--map-path 旧前缀=新路径`，可以给多条，最长的前缀优先。前缀只在整段目录名处匹配，带盘符或 UNC 的 Windows 前缀按路径段比较，忽略 ASCII 大小写，并把 `/` 和 `\` 视为相同。相对前缀和非 ASCII 大小写仍有匹配缺口，见[路线图](roadmap.md)。其他路径只认 `/`，因为 Linux 的目录名里可以有 `\`。相对路径看旧数据目录是哪种写法，推不出旧数据目录时两种斜杠都算分隔符。
  2. 相对路径按旧服务的规则，相对旧数据目录。
  3. 路径在这台机器上原样存在时直接用（比如 Docker 迁移时用 `--volumes-from` 挂了旧容器的卷）。
  4. 路径以旧数据目录开头时，换成这台机器上找到的数据目录，结果算作推测（`guessed`），要 `--accept-guessed` 确认。旧数据目录从 `databaseFolderDir` 或 `coverFolderDir` 推出：0.6.17 启动时会把默认的 `sqlite` 和 `covers` 目录写成绝对路径。

  换出来的路径里的 `.` 和 `..` 段直接丢掉，不跟随。
- **数据库和封面。** `dbUseDefaultPath` 为 `false` 时，数据库在 `databaseFolderDir` 里，换不到这台机器上就拒绝，提示用 `--map-path` 或 `--db`。封面目录取 `coverFolderDir`，换出来的目录不存在，或者和 `sqlite/` 旁边的 `covers/` 是同一个时，按默认位置处理。来源记为 `config.json <键名>`。
- **媒体库。** 报告的预检部分列出每个旧媒体库的类型和它在这台机器上的位置，找不到的写明“not found on this machine”。`--write-config 文件` 按 `--root 旧名=新ID` 为每个旧媒体库写一份 `[[roots]]`，文件已存在时拒绝，权限 `0600`。本地媒体库写换过的路径。OpenList 媒体库写 `url`、`base_path`、`username`，`password_file` 指向目标数据目录的 `secrets/openlist-<ID>.password`，旧密码不读，由用户自己写进这个文件。需要人工处理的地方写成 `# TODO` 注释。缺目录、缺密码文件，或者目录是推测出来的条目整段注释掉，确认后再取消注释，这样服务照样能启动，也不会去扫描一个可能不对的目录。几个旧媒体库对应到同一个新 ID 时，同一个位置只写一份，不同的位置只保留第一个，其余注释掉。`--map-path` 的目标是相对路径时，按当前目录转成绝对路径。合并模式（`--merge`）也可以用 `--root` 和 `--write-config`，这时 `--root` 只决定写出的 ID。
- **抽查。** 每个找到了位置的本地媒体库，按旧作品 ID 均匀取最多 20 部作品，看它们的目录在不在这个位置下。找到的不到一半时，多半是选错了目录或者盘没挂上：报告里写一条问题，`migrate` 先问这个目录对不对，答“否”或者用 `--yes` 时，这个媒体库在配置里保持注释状态。报告的“old library”一行也写出抽查结果。
- **服务启动时的检查。** 数据库里有作品、但 `config.toml` 和设置页都没有定义的媒体库，serve 启动时各打一条 WARN，写出它有多少部作品。这通常是导入后忘了把 `[[roots]]` 合进配置。作品的行都还在，补上媒体库就能播放，不用重新导入。
- `--root` 按最后一个 `=` 切分，因为新 ID 不能含 `=`，旧媒体库的名字却可以。

## 取快照

导入工具先把旧库复制进一个私有的临时目录，之后只打开这份副本，用户的源目录从头到尾不会被写入。

- 复制前后各记一次数据库和 `-journal`、`-wal` 的 `(dev, inode, 长度, 修改时间)`。两次不一致说明复制期间旧库被写过，重新复制一次。仍然不一致时拒绝执行，提示停掉旧服务，因为一直在变的库说明旧服务还在运行。
- 记录和比较都在解析符号链接之后的真实路径上做，因为 SQLite 把日志放在真实文件旁边。
- 非空的 `-journal` 或 `-wal` 也一起复制。默认遇到它们就拒绝执行，提示停掉旧服务、让它正常关闭数据库。旧服务从来不开 WAL，所以崩溃后常见的是 `db.sqlite3-journal`。
- 加 `--recover-journal` 时，导入工具在副本上用读写方式打开一次，SQLite 会回滚热日志或把 WAL 合并回主文件，然后切回 `delete` 日志模式。之后正式读取时用 immutable 方式打开，它会忽略日志文件，所以恢复必须在这一步单独完成。SQLite 没有回滚的日志不是热日志（比如崩溃前日志头还没写下去，全是 0），它不含要恢复的内容，导入工具把副本里的这个文件删掉。源目录里的日志文件保持原样。
- 空的 `-journal` 不算未合并的修改，照常导入。
- 导入工具读完旧库就删掉副本，因为需要的数据已经全部读进内存。

## 旧版本的表结构

支持的旧版本是 0.6.14 到 0.6.17。更早的库直接拒绝，提示先用旧版升级到 0.6.14 以上、启动一次再导入。

- 导入工具打开库后用 `pragma_table_info` 查出每张表实际有哪些列，不按 `knex_migrations` 判断版本，因为执行失败的迁移也会被记进去。`t_work` 没有 `is_custom_meta`（0.6.14 的迁移 `20241110142802` 加的）时，判定为 0.6.14 以前的库。其他必需的表或列缺失时，列出缺了什么，MySQL 版或别的程序的库会在这一步被拦下。
- 全新安装的库用 `schema.ts` 建表，`t_review.work_id` 是字符串列，SQLite 会把数字存成文本。所有作品 ID 读取时都转成整数再比较。
- 0.6.17 新建了 `t_track`，重扫作品时会把 `memo` 改写成只剩 `isContainLyric`，时长只留在 `t_track` 里。所以导入时以 `memo.duration` 为底，再用 `t_track` 里非空的 `duration` 覆盖同一路径的值。`t_track.rel_path` 和 `memo.duration` 的键一样是相对作品目录的路径（0.6.17 的 `migrateDurationsFromMemo` 直接按键复制）。报告里的“track durations from t_track”是这样补上的条数。

## 导入目标

- 目标必须是一个不存在或者为空的目录。目标非空、目标里有正在运行的服务、或者目标和源目录重叠时，导入工具拒绝执行。比较重叠之前先解析符号链接。导入开始写之前，先在目标里用独占方式建一个 `.import-lock`，两个导入同时选中同一个空目录时，只有一个能继续，另一个什么都不写也不清理。导入结束（成功或清理完）后删掉这个文件。
- 所有数据库写入在一个事务里完成。中途失败时，导入工具删掉它在目标里建的所有东西：目标原来不存在就删掉整个目录，原来是空目录就把它清空。这样一个只导入了一半的目录不会被误当成数据目录。清理只删导入工具自己会建的那几个名字，导入期间别的进程放进目标的文件不会被删。收到第一个 SIGINT 或 SIGTERM（比如 Ctrl-C 或 `docker stop`）时，导入工具取消导入：写入每 200 行或 200 张封面检查一次，事务回滚后按上面的规则清理目标。收到第二个信号时直接退出，来不及清理，这时按提示删掉目标目录再重新导入。被 SIGKILL 杀掉时也是这样。
- 写完之后做结构检查：SQLite 的 `integrity_check`、`foreign_key_check`，以及每张表的行数和计划一致。检查不通过按失败处理。
- 导入完成并通过结构检查后，才把这个目录配置成服务的数据目录。
- 需要重新导入时（比如修了映射规则），导入到另一个新目录。不清空正在使用的库。

## 导入前的数据核对

正式写映射代码之前，先在副本上跑一次只读的预检，输出摘要。这一步会改变的是映射细节，不会改变“只读副本、单向导入、对不上就保留并报告”的原则。

1. 核对旧表的列、主键和时间字段，确认播放历史和 review 是否有同一部作品同时出现的情况。
2. 抽几条播放队列和 `memo`，对照实际的文件路径，确认 `subtitle`、`title`、`seconds`、`duration` 的含义和单位。确认 `rate_average_2dp`、`price` 的单位，不从字段名猜。
3. 统计编号前缀和位数、媒体库名、重复编号、重复位置、不能解析的路径各有多少。

### 字段含义

旧作品 ID 是 `前缀序号 × 10^12 + 编号数字`，前缀序号从 0 开始依次对应 RJ、BJ、VJ、CC。编号数字大于等于 1000000 时补齐到 8 位，否则补齐到 6 位。新库另行分配内部 ID，不把旧 ID 当作新作品 ID。作品的 `dir` 相对旧媒体库，不能当成主机绝对路径。

`price` 是日元整数，`rate_average_2dp` 是评分数值，计数字段保留计数语义。`memo.duration` 和播放历史的 `seconds` 使用秒，导入后转换成毫秒。导入使用的旧时间字段是 SQLite `CURRENT_TIMESTAMP` 写入的 UTC 文本，形如 `YYYY-MM-DD HH:MM:SS`，导入时由 SQLite 转成 Unix 毫秒，不按运行机器的本地时区解释。播放队列里的 `subtitle` 是相对目录，`title` 是文件名，补匹配必须使用完整相对路径，不能只比文件名。

这些规则用合成样本验证，不把某一次源库的数量、空表或字段分布当成所有旧安装的合同。

## 映射规则

| 旧表 | 新表 | 规则 |
|---|---|---|
| `t_circle` | `circles` | 直接复制。旧服务手动建的社团 ID 是 0 或负数，API 的 ID 必须是正数，所以这些社团改用 `9000000000 - 旧ID`，比 RG、BG、VG 编码的范围都大，作品的引用跟着改，并在报告里列出 |
| `t_va` | `vas` | 直接复制，ID 保留 |
| `t_tag` | `tags`、`tag_aliases` | 每个旧标签变成一个规范标签，旧名字同时记成它的别名。旧服务从 DLsite 抓到的标签用的就是 DLsite 的标签 ID，之后抓到的同一个标签按 ID 归到它上面 |
| `t_work` | `works`、`work_locations` | 新分配内部 ID，按旧 ID 的顺序插入，旧 ID 到新 ID 的对应关系记进导入报告。`code` 由旧 ID 补齐前缀和位数生成。`root_folder` 和 `dir` 变成这部作品的一行 `work_locations`。`is_custom_meta = 1` 变成 `metadata_src = 'manual'`，其余是 `dlsite`。`rank`、`rate_count_detail` 和时长（`memo` 里的 `duration`，有 `t_track` 时用它覆盖）放进 `extra`，键名是 `rank`、`rate_count_detail`、`legacy_durations`，JSON 的 `null` 和空数组不写。`release` 不是 `YYYY-MM-DD` 格式，或者是 `2024-02-30` 这样日历上没有的日期时，留空并报告。`dir` 是绝对路径或含有 `.`、`..` 这样的路径段时，这部作品跳过并报告，因为它会指到媒体库外面 |
| `r_tag_work`、`r_va_work` | `work_tags`、`work_vas` | 通过 ID 对应关系复制 |
| `t_user` | `users` | `password_hash` 留空，导入后用本地命令设置新密码。`group = 'administrator'` 变成 `is_admin = 1`。`token_version` 取随机初始值。旧表没有创建时间，`created_at` 取导入时间 |
| `t_review` | `favorites`、`play_progress`、`legacy_reviews` | 见下文 |
| `t_play_histroy` | `play_progress`、`import_pending` | 见下文 |
| `t_translate_task` | 不导入 | 不支持迁移歌词翻译任务，报告记录源表数量并计为跳过 |

所有引用旧作品 ID 的地方（关联表、收藏、进度、`legacy_reviews`、封面文件名）都经过同一张对应表转换。

旧库的 `root_folder` 是旧媒体库名。全量导入通过参数显式指定对应的新媒体库 ID，例如合成名称的 `--root Local=local --root Cloud=cloud`。有作品的 `root_folder` 没被映射时，导入失败并列出这些值。`--root` 里写了不存在的旧名字也算失败，因为这多半是拼错了。新 ID 的格式和配置里 `roots[].id` 的要求相同。

导入工具为每个新 ID 写一行 `roots`，`display_name` 取旧的 `root_folder` 名字。启动服务前，配置里的 `[[roots]]` 要用同样的 ID。两个旧名字可以映射到同一个新 ID，但映射之后如果两部作品落在同一个媒体库的同一个目录里，导入拒绝执行。

### review 和播放历史怎么合并

同一个用户的同一部作品，最多只生成一行 `play_progress`。合并规则：

- review 的 `progress = 'marked'` 变成一条收藏，`created_at` 取这条 review 的更新时间。
- review 的 `progress = 'listened'` 提供完成标记：`finished_at` 取这条 review 的更新时间。只有完成标记、没有播放历史时，位置是 0，`updated_at` 也取 review 的更新时间。
- 播放历史提供位置：`updated_at` 取历史记录的更新时间。
- 两者都有时，同时保留完成标记和位置，不按导入顺序互相覆盖。
- 每条 review 都原样复制一份到 `legacy_reviews`，包括 `replay`、`postponed`。
- review 里有评分或短评的，再写一行 `reviews`：评分只取 1 到 5 的整数，其他值丢掉，短评去掉首尾空白，空的当作没有，超过 2000 个字符的截断，`updated_at` 取这条 review 的更新时间。两样都没有的不写。丢掉或截断的都写进导入报告。

播放历史的 `state` 是 JSON，形如 `{queue: [...], index, seconds}`。导入时：

- 先写一行 `play_progress`，`track_id` 留空，`position_ms` 先记旧位置。这时前端显示“无法精确恢复”，不会把旧位置套到第一轨上。
- 把 `queue[index]`、`seconds`、旧行标识，以及这部作品的时长表，写进 `import_pending`，`state = 'pending'`。`source` 是 `{legacy_row: {user_name, work_id}, item, seconds}`，`durations` 是合并后的时长表（`memo.duration` 加上 `t_track`，见“旧版本的表结构”）。
- JSON 解析失败、没有 `queue` 或 `index`、`index` 越界、队列项没有 `title` 时，`import_pending.state` 记成 `unmatched`，`source` 改为 `{legacy_row, raw, reason}`，原始内容照样保存，并计入报告。能读出 `seconds` 时 `position_ms` 仍然记下。`seconds` 缺失、为负或不是数字时按 0 处理。

### 扫描之后补匹配

新版轨道由导入后的第一次扫描生成。较早的旧版本没有轨道表，0.6.17 的 `t_track` 只用于补充旧时长，不直接导入为新版轨道。每次扫描完一部作品，扫描器检查这部作品有没有 `pending` 的导入记录，有就尝试匹配：

- 只在同一部作品的轨道里找。
- 用 `queue[index]` 里的目录（`subtitle`）和文件名（`title`）拼出相对路径，和轨道的 `display_path` 比较，两边都先做 NFC。只看没有缺失、也不是另一个位置的重复副本的轨道。只接受唯一一个完全相同的结果。
- 匹配成功：更新 `play_progress.track_id`，`group_path` 设为这个文件所在的目录（作品根目录是空字符串），`import_pending.state = 'matched'`。位置保持导入时的值。
- 有多个候选：记成 `ambiguous`，保留材料，计入报告。比如同一部作品的两个位置里，同一个路径的文件大小不同。
- 这部作品还有没有完整列举标记的位置时（比如导入时记下的另一个媒体库的位置还没扫描，或上次部分遍历已清空标记），不做补匹配，保持 `pending`。匹配结果不会再回头修改，所以要等所有位置都完整列出。
- 这次扫描里这部作品有位置没能完整列出时，不做补匹配，保持 `pending`，因为没列出的文件可能正是另一个候选。重复副本的判断和补匹配在同一个写事务里完成，另一个媒体库的扫描不会在两者之间插进一个新副本。
- 一个候选都没有：保持 `pending`，下次扫描再试，因为文件可能还没出现（比如另一个位置还没扫描）。扫描摘要里单独计数。
- 用户在新系统里已经播放过这部作品，或者清除了进度：记成 `superseded`，不覆盖新进度。判断方法是 `play_progress.track_id` 已经不为空，或者这一行已经不存在。导入只写空的 `track_id`，只有新系统的播放才会设置它，所以不需要比较时间。

`memo` 里的时长在生成轨道时作为 `duration_ms` 的初始值（`duration_src = 'imported'`），让作品详情马上能显示时长。扫描器从 `works.extra.legacy_durations` 读它，所以没有播放历史的作品也有。这对 OpenList 上的作品尤其有用，因为它们要到第一次播放才会被探测。后台的 ffprobe 照常运行，结果会覆盖它，因为导入的时长不包含 codec 这些信息。

## 路径的几条规则

- **Windows 来源的库。** 旧库里有作品目录用 `\` 而没有任何目录用 `/` 时，判定这个库是在 Windows 上写的，作品目录、`memo` 里时长表的键和播放历史队列项的 `subtitle` 都把 `\` 换成 `/`。在 Linux 和 macOS 上文件名可以合法地含有 `\`，所以只要有一个目录用 `/`，就一个都不换。预检报告里会写明做了这种转换。
- **NFC。** `rel_path` 原样保存，只在比较时做 NFC。macOS 写的文件名是 NFD，同一个名字的 NFC 和 NFD 两种写法算同一个位置。
- **不越出媒体库。** 作品目录除了按 `/` 切分后不能有 `..` 和 `.`，还要过主机自己的路径解析：每一段都必须是普通的名字。在 Windows 上 `..\x`、`C:x`、`\\srv\x` 和以 `\` 开头的路径因此也会被拒绝。Windows 上的这些用例至今没有运行过：桌面版的 Windows 工作流只构建安装包和跑 WebView2 端到端测试，不跑 `cargo test`。
- **`--json` 和退出码。** `--dry-run --json` 把报告和拒绝理由输出成 JSON。预检发现导入会拒绝时，退出码是 2，其他失败是 1，这样脚本能区分“会拒绝”和“检查不了”。

## 合并到已有的库

新库里已经有作品时（比如桌面版用过一段时间，或者服务器已经扫描过媒体库），导入不替换整个库，只合并用户数据：收藏、review 和播放进度。旧库里的作品、元数据、封面、标签和声优都不导入，作品由新库自己扫描得到。命令行是 `import-legacy --merge --data-dir <已有的数据目录>`，桌面版的外壳调用 `embed::Server::merge_legacy`，在运行中的服务上执行。

- 先用和完整导入相同的规则生成导入计划（`plan::build`，不给 `--root`），从中取出每个旧用户在每部作品上的收藏、review 和进度。完整导入的其他规则（编号、日期、播放队列的解析）完全一样。
- 旧用户合并到同名账号。`--user OLD=NEW` 把一个旧用户合并到另一个名字的账号，桌面版用它把旧用户合并到本机账号。没有同名账号时新建一个没有密码、不是管理员的账号，因为新库已经有自己的管理员。
- 所有数据先按“用户 + 作品编号”写进 `legacy_user_state`，同一用户和编号再次合并时覆盖旧行。新库里已经有这个编号的作品，同一个事务里马上挂上去。没有的留在表里，等扫描新建这部作品时由扫描器挂上，然后照常补匹配进度。作品还没扫描到时，它的收藏和进度不显示。
- 挂上去的规则：收藏和 review 在新库已经有同一条时保留新库的，`reviews` 也一样，新库里已经评过的作品不被旧数据覆盖。进度按 `updated_at` 保留更新的一条。旧进度更新时，写入 `play_progress`（`track_id` 为空）和 `import_pending`，之后按“扫描之后补匹配”对到轨道。旧进度没有可匹配的播放队列时，删掉这部作品原有的 `import_pending`，因为那份材料属于被替换的进度。
- 几个旧用户合并到同一个账号时，先按同样的规则合成一份：收藏取更早的时间，进度取更新的，review 取有评分或短评的那条。
- 合并前检查目标库和它的数据库文件（解析符号链接之后）不在旧数据的任何目录里，因为合并会以写方式打开它。实际合并时也先打印导入计划的报告，跳过的旧记录和原因都在里面。
- 合并在一个事务里完成，失败时什么都不写。它不需要停服务，也不碰作品、位置和媒体库表。旧媒体库的路径用 `--write-config` 另外写出来，见“读旧的 config.json”。

## 封面

旧的 `covers/` 目录里每部作品有三张图，文件名形如 `RJ01234567_img_main.jpg`、`_img_sam.jpg`（小图）和 `_img_240x240.jpg`（方形缩略图）。导入工具只复制 `main`，按新作品 ID 存成 `covers/{id}.jpg`，`cover_src = 'imported'`。缩略图由新后端按需重新生成。`imported` 的封面不会被普通的元数据刷新覆盖。

## 引导式迁移

`migrate` 复用导入计划和执行器，根据目标是否已有库选择全量或合并。它询问路径和映射，确认推测路径及日志恢复，再写媒体库配置和账号密码。非交互调用必须显式选择默认答案，且不设密码。已有配置不被覆盖，草稿写入另一文件，未确认路径或缺凭据的条目保持注释。

旧容器迁移由宿主机脚本读取已停止容器的配置、数据库和封面，在新镜像中调用同一个引导入口，不启动源容器。暂存副本和新卷的所有权、失败清理及挂载遮蔽属于脚本边界。源容器原数据始终不写，新服务的挂载与配置仍需管理员核对，具体步骤见[迁移指南](https://github.com/QWERChin/kikoeru-neo/blob/main/docs/zh-CN/migration.md)。

## 导入报告

报告开头列出旧库和封面目录的路径及来源（见“找旧数据”）。之后按表分开统计：源记录数、成功导入、合并、跳过，以及 `import_pending` 里 `matched`、`ambiguous`、`unmatched`、`superseded` 各有多少。每一条跳过和对不上的记录都写出原因和原始内容的位置，比如 `t_play_histroy user=admin work_id=123456`。

预检和导入用同一份内存里的导入计划，所以两边的数字一定相同。摘要打印到标准输出。导入成功后，完整的报告连同旧 ID 到新 ID 的对应表另存为数据目录里的 `import-report.json`，权限 `0600`。导入时 `import_pending` 只会有 `pending` 和 `unmatched`，另外几种状态由扫描后的补匹配产生。

验收比较本次预检、导入报告和目标库，不使用固定的作品或轨道数量。收藏、评价和播放历史可能重叠，进度行数应按映射规则计算，而不是直接相加。扫描后另行核对 `import_pending` 的状态和无法匹配的原因，不能把扫描新发现的作品算成导入差异。
