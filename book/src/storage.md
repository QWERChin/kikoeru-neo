# 存储后端

一个媒体库（root）是包含作品目录的媒体根目录，可以在本地磁盘上，也可以在 OpenList 或 WebDAV 服务器上。每个媒体库由一个存储后端实现，后端要回答三类问题：这个目录下有什么、服务端怎么读一个文件、浏览器该怎么访问它。

配置字段、存储账号前提和扫描操作见[媒体库与扫描](https://github.com/QWERChin/kikoeru-neo/blob/main/docs/zh-CN/libraries.md)。本章保留后端接口与访问边界。

## 接口

下面是核心接口的节选，完整定义在 `crates/neo-storage/src/lib.rs`。

```rust
#[async_trait]
pub trait Storage: Send + Sync {
    /// 列出一个目录的全部直接子项。分页由实现内部读完；
    /// 任何一页失败都返回错误，不返回部分结果。
    async fn list(&self, dir: &RawPath) -> Result<Vec<Entry>, StorageError>;
    async fn stat(&self, path: &RawPath) -> Result<Entry, StorageError>;

    /// 服务端自己读文件，用于 ffprobe、转码、读字幕和打包下载。
    async fn source(&self, path: &RawPath) -> Result<Source, StorageError>;

    /// 告诉 HTTP 层浏览器该怎么拿到这个文件。
    async fn access(&self, path: &RawPath) -> Result<Access, StorageError>;

    /// 列出目录下的整棵树，目录排在它的内容之前。默认实现逐层调用 list，
    /// 任何一层失败整个调用失败。
    async fn walk(&self, dir: &RawPath) -> Result<Vec<WalkEntry>, StorageError>;
    /// 返回可读部分以及失败目录的相对路径和原因。起始目录失败仍返回 Err。
    async fn walk_partial(&self, dir: &RawPath) -> Result<PartialWalk, StorageError>;
    fn list_concurrency(&self) -> usize;
}

pub struct PartialWalk {
    pub entries: Vec<WalkEntry>,
    pub failed: Vec<(RawPath, StorageError)>,
}

pub enum StorageError {
    NotFound,          // 远端明确回答“不存在”
    Unavailable(String),       // 连不上、超时、登录失败、分页中途失败、被限流且超出等待预算
    Upstream(String),  // 远端返回了业务错误
}

pub enum Source {
    LocalFile(LocalFile),   // 已经打开的文件句柄，见下文 local
    Remote(RemoteFile),     // 经存储后端打开的远端文件，见下文 openlist
}

pub enum Access {
    ServeLocal(LocalFile),  // 后端自己按 Range 返回
    Remote(RemoteFile),     // 后端代理转发
}

pub struct RemoteFile {
    pub size: Option<u64>,
    pub mtime_ms: Option<i64>,
    pub opener: Arc<dyn RemoteOpen>,  // open(headers) -> 状态码、响应头、字节流
}
```

`RawPath` 是原始字节形式的相对路径，见[数据模型](data-model.md)的设计原则。它在构造时就拒绝绝对路径、空的路径段、`.`、`..` 和 NUL，所以拼到媒体库根目录上不可能跳出去。它不拒绝 `\`，因为很多 Shift_JIS 字符（比如 `ソ`）的第二个字节就是 0x5C。`\` 只在 openlist 后端的边界上拒绝，见下文。`list` 返回的条目带类型：文件、目录、符号链接和其他（设备、管道等）。符号链接照样列出来，让扫描器能写进日志，但不会被跟随或打开。

这些类型在 `neo-storage` crate 里，播放、扫描和三种存储后端都用它，不各自定义。

`walk_partial` 中的条目和失败路径都相对于起始目录。每次 `list` 必须完整成功，失败目录的任何条目都不能混入结果，但兄弟目录继续遍历。父目录列出的失败子目录项仍可保留在条目中，它只说明父目录见过这个名字，不能证明子目录已列出。调用方必须排除失败路径本身及其后代，不能把它们当作已见到或缺失。遍历中子目录返回 `NotFound` 表示树在变化，记录为 `Unavailable`，起始目录失败则保留原来的错误分类。原有 `walk` 仍只返回完整树，任何列举失败都会使整个调用失败。

三种后端的部分遍历共用 `list` 边界。OpenList 继续使用客户端的缓存、准入和限流，并按路径排序结果以保持写库顺序。这里不直接使用 `openlist-client::walk_partial_from`，因为它排除所有重名项，而扫描的现有规则保留第一项并记录重复名称。部分遍历保留重复条目供扫描器处理，但同一目录只遍历一次。

`NotFound` 和 `Unavailable` 必须分清楚，因为扫描器只把 `NotFound` 当作“确认缺失”的依据。本地目录没挂载、网盘超时、登录失败、分页失败、解析失败、被限流，都是 `Unavailable`。

三种后端列出媒体库根目录时，即使请求成功，只要没有任何子项就返回 `Unavailable`，从根目录开始的 `walk` 也遵守这个规则。扫描因此保留这个媒体库已有的位置、作品和轨道，不把空根目录当作全部删除的依据。这个保护只用于媒体库根目录，空子目录仍返回空列表。真正的空媒体库首次扫描也会失败，加入内容后才能正常扫描。

## local

直接读本地文件系统，`access` 返回 `ServeLocal`。

- 所有路径都在媒体库根目录下解析，解析后检查是否仍在根目录内，防止 `../` 穿出去。
- 不跟随符号链接。扫描遇到符号链接时跳过并写进扫描日志。路径中任何一级是符号链接时，按 `NotFound` 处理。
- 这两条由内核在打开时保证：所有路径都相对于媒体库根目录的句柄，在 Linux 上用 `openat2` 加 `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS` 打开。macOS 没有 `openat2`，桌面版在那里逐段打开：每一段都相对于上一段已经打开的目录，带 `O_NOFOLLOW`，路径里又没有 `..`，效果相同。Linux 上 `openat2` 返回 `ENOSYS` 时也改用逐段打开。5.6 以前的内核没有这个系统调用，systemd 的 `RestrictSUIDSGID=` 也会让它一律返回 `ENOSYS`，因为 seccomp 看不到它放在结构体里的标志。Windows 没有相对目录句柄的打开，桌面版逐段用 `symlink_metadata` 拒绝符号链接和 junction，打开时不跟随最后一段的重解析点，再用 `GetFinalPathNameByHandleW` 确认这个句柄的真实路径仍在根目录下，所以检查和打开之间换掉目录也会被发现，列目录也从这个句柄读，不再按路径查找。Windows 上交给 ffmpeg 的是文件路径而不是句柄，因为那里没有 `/dev/fd`。ffmpeg 按路径重新打开文件，这一步仍可能被换掉的目录引到媒体库外面。桌面版以媒体库主人的身份运行，能换掉目录的人本来就能读这些文件，所以先记为已知限制。先检查路径再按名字打开是不行的，中间目录可能被换成符号链接。同样的原因，`source` 和 `access` 返回已经打开的文件句柄（`LocalFile`），调用方直接读它，不按路径重新打开。交给 ffmpeg 时，把句柄作为继承的描述符或标准输入传过去，让它打开 `/dev/fd/N`，这样仍然可以 seek。
- 管道、设备这类特殊文件不会被打开，按 `NotFound` 处理。
- 列出的条目按文件名的字节顺序排好，所以同一个目录每次列出的顺序都一样。
- 媒体库根目录本身不存在时（比如外置硬盘没挂上），整个媒体库返回 `Unavailable`，不当作空目录。某个路径不存在时，先确认根目录还在、并且不是空的，再返回 `NotFound`，因为硬盘被拔掉时所有路径会同时消失。根目录是挂载点时，卸载之后留下的是一个空目录，所以空的根目录也按 `Unavailable` 处理，列出根目录时同样如此。代价是一个真的空媒体库第一次扫描会报“没有挂载”，放进第一部作品就好了。权限不足等其他错误都是 `Unavailable`。

## openlist

OpenList 后端只是一层很薄的适配，真正和 OpenList 打交道的代码放在一个独立的库 `openlist-client` 里，见下文。115 网盘挂在 OpenList 上，kikoeru-neo 不知道也不关心底下是哪种网盘，不做任何 115 专门的处理，也不让浏览器直接访问网盘直链。

### 访问方式

浏览器只跟 kikoeru-neo 通信，`access` 总是返回 `Remote`：后端通过 `openlist-client` 用 `fs/link` 拿到直链和必须带的请求头，自己去拉文件，再转发给浏览器。`RemoteFile` 不暴露直链，只给一个 `open` 方法，直链的缓存、过期重取和限流都留在 `openlist-client` 里。这样不用关心直链能不能从手机访问、有没有过期，也不会把网盘凭据暴露给浏览器。代价是播放的流量要经过 kikoeru-neo 这台机器。

代理的规则：

- 上游返回 200、206、416 时，状态码和 `Content-Length`、`Content-Range`、`ETag` 等允许的响应头转发。上游忽略 Range 返回 200 时，不伪造成 206。
- 还没开始向浏览器发送响应体时，如果上游返回 401、403 或 404，说明直链可能过期了：作废缓存的直链，重新调一次 `fs/link`，再试一次。还是失败就返回 502。
- 已经发出一部分字节之后上游断开，直接结束这个响应，不在后面追加 JSON。播放器会自己重新请求，从当前位置继续。
- 浏览器断开时，立即取消上游请求。转发通过容量为 8 个 `Bytes` 块的通道施加背压，不承诺固定的字节上限。客户端持续 60 秒不读取时结束转发并释放传输名额。
- 只转发浏览器播放和拖动需要的响应头（长度、范围、`ETag`、`Last-Modified`、`Accept-Ranges`），网盘的 Cookie 和缓存规则不转发。浏览器的请求头里也只转发 `Range` 和 `If-Range`。`Content-Type` 从不转发，总是用按扩展名和 probe 得出的类型，并加上 `X-Content-Type-Options: nosniff`：网盘给的类型可能是 HTML 或 SVG，浏览器会把它当作本站的脚本执行，而 API token 就存在本站。
- `HEAD` 不打开远端文件，用列表里的大小直接回答。

直链按路径缓存，缓存时间取 `fs/link` 返回的有效期和 10 分钟两者中较短的那个。拖动进度条会产生很多 Range 请求，它们都复用同一个直链，不会每次都去取链。

OpenList 媒体库只读。重命名、上传、删除这些写操作以后按需逐项开放。

### 列目录优化

扫描 OpenList 媒体库时，最贵的不是列目录，而是取直链和刷新目录：OpenList 通常从自己的目录缓存回答 `fs/list`，而取直链和强制刷新每次都会打到网盘，115 会限流。所以优化的方向是尽量少调这两种请求，并且让列目录的并发可控：

- **发现与同步以列目录为主。** 发现作品和同步轨道使用 `fs/list`。读取文件夹封面时会取直链并下载图片。ffprobe 和音频分析放到第一次播放或按需请求时再做（见[扫描阶段中的探测时长规则](scanning.md#阶段)）。
- **完整扫描不刷新 OpenList 缓存。** 后端调用普通的 `Client::list`，没有调用 `Client::refresh`。`full` 只关闭作品目录摘要跳过，不能保证重新取得网盘目录。当前也没有单作品重新扫描接口。
- **跳过没变的作品。** 每次完整列出一个作品目录后，把第一层所有条目的名字、类型、大小、修改时间算成一个摘要，存进 `work_locations.listing_hash`。子目录的修改时间也在里面，代表它下面的内容。下次扫描先只列出作品目录的第一层，摘要没变就跳过这部作品的深层遍历，也不写数据库。位置被标记缺失时摘要清空，再次找到时一定完整遍历，把轨道恢复回来。子目录列举失败的部分遍历也清空摘要和 `listed_at`，不保存本次摘要，因此下一次扫描仍会遍历整部作品。这条规则用于 OpenList 和 WebDAV 媒体库：本地列目录很便宜，而且本地目录的修改时间不会因为更深一层的文件变化而改变。目录修改时间是否传播深层变化取决于远端实现，不可靠时，管理员用 `POST /api/admin/scan` 的 `"full": true` 强制完整遍历每部作品。
- **分类控制请求速率。** 列目录、取直链、文件传输各有自己的限额，规则见下文 `openlist-client`。

### openlist-client

这是独立的 Rust 库，负责 OpenList API、缓存和限流：

- 登录和 token 刷新，收到登录失效时重新登录 1 次。
- `fs/list`（读完所有分页，任何一页失败整个调用失败）、`fs/get`、`fs/link`，同时检查 HTTP 状态码和响应体里的业务 `code`。
- 按请求类型分别限流：
  - 列目录限制同时进行的请求数（默认 4）。
  - 取直链按每秒请求数限速（默认 1）。`fs/get` 也算取直链，因为 OpenList 处理它时会向网盘要下载地址。
  - 同一个文件的取直链请求合并成一次。没有人再等结果的取直链（比如浏览器已经断开）立刻取消，让出排队的位置，不然在每秒 1 次的限速下，一串断开的请求会让后面别的用户等上很久。同时在排队的不同文件最多 32 个，再多的请求直接得到“暂时无法访问”（503），因为队列再长也只会让每个人等得更久。
  - 文件传输不按速率限流，只限制同时打开的传输数（默认 16）。这个限额和 API 请求的并发分开计算，因为播放器会把一个传输开着好几分钟，不能因此挡住列目录。传输同样遵守下面说的 429 和 503 暂停。网盘对传输返回 429 或 503 时只暂停后续的传输，最长 5 分钟，不影响 API 请求，因为这个等待时间来自网盘的服务器而不是 OpenList。
- 识别网盘限流：115 被限流时返回错误码 770004（“已达到当前访问上限”），OpenList 有时会把它转成不带消息的 500。遇到时这一类请求的速率减半，之后每连续成功 20 次再慢慢恢复。一次调用不管重试几次最多减半一次，否则一个总是失败的文件就能把速率压到最低。
- 遇到 429 和 503 时，整个客户端暂停发新请求，按 `Retry-After` 或带抖动的退避等待。每次调用（包括它的重试）有自己的等待预算，默认 120 秒，暂停超出预算时立即返回 `Unavailable`，不空等。已经在排队的请求拿到名额后会再检查一次暂停，不会趁暂停期间发出去。OpenList 登录失败太多次时会在 200 响应里返回业务 `code` 429，而且不给 `Retry-After`，这时同样暂停整个客户端 60 秒，因为继续尝试登录只会延长锁定。预算按调用计算而不是整个进程只有一份，因为服务会长期运行，一次限流不能让之后所有请求都失败。
- 可重试的错误最多试 3 次。强制刷新和写操作只发 1 次。

为了少发请求，库在内存里缓存结果，并合并同时发生的相同请求：

- 目录列表按路径缓存，默认 5 分钟，最多 4096 个目录。强制刷新的结果直接替换缓存，但如果刷新期间这个目录被作废（比如刚做过写操作），刷新的结果不写进缓存。
- 直链按路径缓存，时间取 `fs/link` 返回的有效期和 10 分钟中较短的那个，最多 1024 条。代理收到上游 401、403、404 时只作废这一条直链，不影响别的文件。
- 同一个目录或同一个文件的请求如果已经在进行中，后来的调用等这一个结果，不再另发请求。失败的结果也共享给所有等待者，但不进缓存，所以一次限流不会被每个等待者各重试 3 次。最后一个等待者离开时取消共享请求，避免继续占用限流名额。
- 查单个文件（`stat`）从父目录的列表里找，不调 `fs/get`。列表已经超过 5 秒还找不到时，重新列一次父目录再确认，避免把刚加进来的文件当成不存在。5 秒内的列表直接相信，所以连续查很多不存在的文件最多只多列一次。
- `fs/list` 默认 `per_page = 0`，一次拿回整个目录。OpenList 每处理一页都会构造完整的目录列表再切片，分页只会增加请求数。如果配置了分页，只有第一页带 `refresh`，否则每一页都会让网盘重新列一次。

错误分类上，只有 OpenList 的消息里带 `object not found` 才算 `NotFound`。存储没挂载（`storage not found`）、登录失败、被限流、分页对不上总数都算 `Unavailable`。和本地媒体库一样，如果媒体库的 `base_path` 本身返回 `NotFound`，或者成功列出但没有任何子项，openlist 存储后端按 `Unavailable` 处理，不把整个库当成空的。空列表的错误消息包含根路径，并提示检查 OpenList 的基础路径是否正确。

路径里不允许出现 `\`。OpenList 处理路径时先把 `\` 换成 `/` 再做清理，`a\..\..` 这样的名字会跳出媒体库目录。网盘上名字带 `\` 的文件，列它所在的目录时整个调用失败（`Upstream`），这个目录的列表也不进缓存，扫描器会报告，不会当作缺失。

`fs/link` 只允许管理员调用，而且不拼接账号的基础路径，所以 kikoeru-neo 用的 OpenList 账号要是管理员，基础路径设为 `/`。

目录摘要由库提供（`Listing::digest`）：对每个条目的名字、类型、大小、修改时间按名字排序后算 SHA-256，存成 64 位十六进制。条目的 `sign` 会随时间变化，哈希值有的网盘要延迟才给，都不参与摘要。

库位于公开仓库 `https://github.com/chinrw/openlist-client`，使用 MIT 许可证。kikoeru-neo 在根目录的 `Cargo.toml` 里按 `rev` 固定一个提交依赖它，升级就是改这个提交并跑完整的检查。它不依赖任何 `neo-*` crate，自己的测试和 CI 在那个仓库里。`neo-storage` 的测试里留着一份同样的假 OpenList，用来测 openlist 存储后端。对它的修改提到那个仓库，不在 kikoeru-neo 里改。

## webdav

只读的 WebDAV 媒体库，用于 NAS、Nextcloud、`rclone serve webdav` 这类已经提供 WebDAV 的地方，不需要另装 OpenList。和 OpenList 一样，浏览器只跟 kikoeru-neo 通信，`access` 返回 `Remote`，由后端带着凭据去取文件再转发，代理规则和上面 OpenList 的“访问方式”相同，只是没有直链：每次播放都直接 `GET` 这个文件。

### 地址和登录

- `url` 是 WebDAV 服务的根地址，只接受 `http` 和 `https`，比如 `https://nas.example.lan/dav`。`base_path` 是媒体库在这个服务下的目录，比如 `/media/works`。请求的地址是 `url` 的路径、`base_path` 和媒体库内的相对路径依次拼起来，每一段名字都做百分号编码。
- 只支持 HTTP Basic 认证，每个请求都带上。用户名和密码的规则和 OpenList 一样：配置文件里用 `password_file`，它可以指向 `secrets/roots/` 内的文件且受回收保护。界面添加的使用数据库引用的版本化密码文件，发布和旧格式兼容规则见[配置与持久状态](config.md#媒体库密码的发布与回收)。服务器回答 401 或 403 时整个媒体库按 `Unavailable` 处理，不当作文件缺失。
- 重定向只跟随同一个来源（协议、主机、端口都相同）的，最多 5 次，因为跟到别的主机会把 Basic 凭据带过去。跨来源的重定向按 `Upstream` 处理。

### 列目录

- `list` 发 `PROPFIND`，`Depth: 1`，请求体只要 `resourcetype`、`getcontentlength`、`getlastmodified` 和 `getetag` 四项。不用 `Depth: infinity`，很多服务器关掉了它，开着的也可能一次返回整个网盘。
- 207 响应里每个 `response` 单独处理：`href` 先做百分号解码，再去掉请求目录本身那一项。必须正好是请求目录的直接子项，否则整个调用失败（`Upstream`）。名字是 `.`、`..`、空的，或者含 `/`、`\`、NUL 时同样失败，和 OpenList 不允许 `\` 的理由一样。`href` 可以是绝对 URL 或者绝对路径，两种都按请求的来源解析。
- 每一项取状态为 200 的 `propstat`，404 的 `propstat` 只表示服务器没有这个属性。其他失败状态让整个调用失败，按下文的错误分类处理，不能因为同一项的另一个属性查询成功就忽略失败。`resourcetype` 里有 `collection` 的是目录，其余是文件。大小缺失时记为未知，修改时间按 HTTP 日期解析，解析不了时记为未知。
- `stat` 发 `Depth: 0` 的 `PROPFIND`。

### 读文件

- `source` 和 `access` 都是 `GET`，带浏览器的 `Range` 和 `If-Range`。上游忽略 Range 返回 200 时照样转发 200，和 OpenList 的规则一样。
- `HEAD` 用列表里的大小回答，不打开远端文件。列表里没有大小时，回答不带 `Content-Length`，也不打开远端文件。
- 同时打开的传输数默认最多 16 个，列目录的并发默认 4 个（`list_concurrency`），两者分开计算。

### 错误分类

- `404` 和 `410` 是 `NotFound`。和本地、OpenList 一样，先用 `Depth: 0` 确认 `base_path` 本身还在，再报告缺失。`base_path` 本身 404 时整个媒体库按 `Unavailable` 处理，不当成空的。
- `base_path` 的 `Depth: 1` 请求成功，但去掉请求目录本身后没有子项时，按 `Unavailable` 处理。错误消息包含根路径，并提示检查 WebDAV 的基础路径是否正确。空子目录不受这个保护影响。
- 连不上、超时、401、403、`423 Locked`、`429`、5xx 都是 `Unavailable`。429 和 503 按 `Retry-After` 等待，没有时用带抖动的退避，每次调用最多等 120 秒，和 `openlist-client` 的预算一样。连接错误和 5xx 最多试 3 次。
- 207 解析失败、`href` 不合规则、服务器返回 HTML 登录页这类意外的成功响应，都是 `Upstream`。

### 目录摘要

WebDAV 媒体库和 OpenList 一样按目录摘要跳过没变的作品（见上面的“列目录优化”）：作品目录第一层每个条目的名字、类型、大小、修改时间和 `getetag` 按名字排序后算 SHA-256。很多服务器（比如 Nextcloud）的目录 ETag 会在里面任何一层变化时改变，这样深层的变化也会让摘要变。不改目录 ETag 的服务器上，深层变化要靠 `"full": true` 的完整扫描。

## 配置来源

媒体库可以来自只读文件配置或数据库。两种来源复用相同的校验与存储实现，文件配置在网页中只读，数据库媒体库通过管理接口即时更新。远端凭据不直接放进只读配置，数据库媒体库把密码作为数据目录中的私有文件保存。配置示例与操作步骤见[媒体库指南](https://github.com/QWERChin/kikoeru-neo/blob/main/docs/zh-CN/libraries.md)。
